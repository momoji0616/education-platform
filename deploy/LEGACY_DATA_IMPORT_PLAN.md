# 旧教学数据安全导入方案

本文档给出 [piclass2.sql](/E:/education-platform/backend/sql/piclass2.sql) 融入当前教育平台的安全执行顺序。

目标：

- 不破坏现有若依业务库
- 不直接污染当前用户和权限体系
- 先建立隔离区，再逐步映射到当前教育系统

## 1. 执行原则

### 必须遵守

- 旧库先导入隔离库，不直接导入当前主业务库
- 先做结构验证和样本核对，再做批量清洗
- 先接题库和作答数据，再接作业与班级关系
- 任何账号映射都不能直接覆盖现有若依账号表

### 建议库划分

推荐新增独立库：

- `education_legacy_piclass`

或新增独立前缀表：

- `legacy_piclass_*`

更推荐独立库，便于回滚和核验。

## 2. 分阶段导入

### 阶段一：原始导入

目标：

- 保留原始数据
- 不做业务改造

执行内容：

1. 将 `piclass2.sql` 导入隔离库
2. 校验核心表记录数
3. 确认字符集、主键、外键是否正常

重点核对表：

- `tk_choice1`
- `tk_choice2`
- `dt_choice`
- `dt_program`
- `zy_assign`
- `zy_detail`
- `zy_score`
- `student`
- `class`

输出结果：

- 原始库可查
- 可抽样验证题目、答案、作答记录

### 阶段二：中间清洗层

目标：

- 把旧库字段整理成当前系统可理解的数据模型

建议新增中间表：

- `legacy_question_bank_clean`
- `legacy_student_answer_clean`
- `legacy_assignment_clean`
- `legacy_assignment_question_clean`
- `legacy_assignment_score_clean`
- `legacy_student_profile_clean`
- `legacy_class_clean`
- `legacy_user_bind_clean`

清洗动作：

- 统一编码为 UTF-8
- 将题干与选项拆分
- 将字符型分数字段转数值
- 标记题型
- 去除无效学生编号和异常空值
- 标注旧系统来源

### 阶段三：业务映射层

目标：

- 将中间层数据映射到当前教育平台业务表

建议生成的新业务表：

- `edu_question_catalog`
- `edu_question_bank`
- `edu_student_answer_record`
- `edu_assignment`
- `edu_assignment_question`
- `edu_assignment_score`
- `edu_student_profile`
- `edu_class`
- `edu_legacy_user_map`

### 阶段四：功能接入

目标：

- 让当前页面真正消费这批数据

接入优先级：

1. 学生端智能刷题
2. 学生端学业诊断
3. 教师端班级学情分析
4. 教师端试卷生成
5. RAG 知识增强
6. 成绩预测升级

## 3. 每阶段建议检查项

### 原始导入后检查

- 表数量是否完整
- `tk_choice2` 是否能正确读出题目和答案
- `dt_choice` 是否能按学生查到作答记录
- `dt_program` 是否能读出代码和分数
- `zy_assign` 与 `zy_detail` 是否能关联

### 清洗后检查

- 同一题目是否存在重复
- 选项是否拆分正确
- 正确答案是否保留
- 编程题代码是否保留换行
- 作业与题目是否能回连
- 学生编号是否稳定

### 业务映射后检查

- 学生能否按学号查到全部答题记录
- 班级是否能统计章节正确率
- 作业是否能还原出题目列表
- 教师是否能查看作业整体得分结构

## 4. 功能落地顺序建议

### 第一批

只接入：

- 题库
- 选择题作答记录

直接带来的功能：

- 学生智能刷题推荐
- 学业诊断
- 错题本
- 教师章节正确率分析

### 第二批

再接入：

- 编程题记录
- 作业表
- 作业得分表

直接带来的功能：

- 编程题薄弱项分析
- 教师作业讲评
- 班级作业质量分析

### 第三批

最后接入：

- 班级关系
- 用户绑定

直接带来的功能：

- 自动归班
- 教师班级权限隔离
- 学生本人数据隔离

## 5. 风险与应对

### 风险一：旧用户体系冲突

风险：

- 旧 `user` 表可能与当前若依 `sys_user` 体系不一致

应对：

- 不直接导入主用户表
- 只做 `legacy_user -> current_user` 绑定表

### 风险二：字符编码历史问题

风险：

- 部分文本可能出现乱码

应对：

- 导入时统一 `utf8mb4`
- 清洗脚本中做异常字符检测

### 风险三：大体量 SQL 直接执行失败

风险：

- SQL 约 138MB，直接在主库执行风险高

应对：

- 先隔离库导入
- 分表验证
- 再生成精简后的导入脚本

### 风险四：题型含义不完全明确

风险：

- `zy_detail.type` 等字段可能存在旧系统约定

应对：

- 先抽样核对样本
- 再固化枚举字典
