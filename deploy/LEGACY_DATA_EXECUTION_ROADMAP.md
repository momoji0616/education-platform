# 旧教学数据接入总路线

本文档用于统一后续旧教学数据的接入节奏，目标是：

- 尽可能把 `piclass2.sql` 中的高价值数据用到现有功能中
- 不直接污染当前业务主库
- 不破坏现有主控端、教师 Pad、学生 Pad 的角色边界
- 先稳定、后增强，优先确保不出错

关联文件：

- [piclass2.sql](/E:/education-platform/backend/sql/piclass2.sql)
- [LEGACY_DATA_MAPPING.md](/E:/education-platform/deploy/LEGACY_DATA_MAPPING.md)
- [LEGACY_DATA_IMPORT_PLAN.md](/E:/education-platform/deploy/LEGACY_DATA_IMPORT_PLAN.md)

## 一、当前结论

这份旧 SQL 不能直接导入当前主业务库，原因主要有：

1. 它是完整旧平台库，不是单一题库或成绩数据包
2. 表之间存在完整外键链，尤其是：
   - `user`
   - `class`
   - `student`
   - `zy_assign`
   - `zy_detail`
   - `zy_score`
3. 旧 `user` 体系与当前若依权限体系不一致
4. 当前项目需要的是“数据融合”，不是“旧系统整库覆盖”

因此后续必须走：

`隔离库 -> 中间清洗层 -> 新业务表 -> 页面/接口接入`

## 二、总实施顺序

### 阶段 0：冻结原则

在任何真正导库前，必须遵守：

- 不向当前主库直接执行 `piclass2.sql`
- 不覆盖当前若依用户、角色、菜单、权限体系
- 不把旧表名直接作为现有业务表使用
- 所有旧数据接入必须保留 `source_system='piclass2'`

### 阶段 1：建立隔离区

目标：

- 安全保存旧数据原貌

执行内容：

- 新建隔离库，例如 `education_legacy_piclass`
- 将 `piclass2.sql` 导入隔离库
- 验证核心表可查询

交付结果：

- 一个完整可追溯的旧数据仓

### 阶段 2：建立中间清洗层

目标：

- 把旧表字段整理成当前系统能稳定消费的结构

执行内容：

- 新建中间表
- 把题干、选项、答案、解析拆分
- 将成绩、分数、题型做标准化
- 清理乱码和脏数据

交付结果：

- 干净的 `legacy_*_clean` 表

### 阶段 3：建立新业务表

目标：

- 为当前教育平台提供正式数据来源

执行内容：

- 新建 `edu_question_bank`
- 新建 `edu_student_answer_record`
- 新建 `edu_assignment`
- 新建 `edu_assignment_question`
- 新建 `edu_assignment_score`
- 新建 `edu_student_profile`
- 新建 `edu_class`

交付结果：

- 现系统可直接消费的规范业务表

### 阶段 4：按功能逐步接入

目标：

- 让这些数据真实增强当前功能

推荐顺序：

1. 学生端智能刷题
2. 学生端学业诊断
3. 教师端班级学情分析
4. 教师端智能题库与组卷
5. RAG 题库与解析问答增强
6. 学习规划与成绩预测增强

## 三、功能增强目标

### 学生端

优先增强：

- 智能习题生成与个性化刷题推荐
- 多维度学业诊断报告
- 个性化学习规划
- RAG 学业问答

预期变化：

- 不再只展示静态建议
- 可以基于真实错题、章节、课程、作业表现生成建议

### 教师端

优先增强：

- 班级学情智能分析
- 智能题库与试卷生成
- AI 作业讲评助手
- 编程题分析

预期变化：

- 教师端图表将由真实做题数据驱动
- 可以按课程和章节做教学策略建议

### 主控端

可后续增强：

- 年级/班级课程热力图
- 课程难点分布
- 作业完成率总览

## 四、风险控制要求

### 高风险操作

以下操作在没有单独确认前禁止执行：

- 把 `piclass2.sql` 直接导入当前主库
- 将旧 `user` 表导入当前若依用户表
- 直接重命名旧表替换现有业务表
- 直接在页面里改成调用旧表

### 低风险推进顺序

安全顺序必须是：

1. 先文档
2. 再建中间表
3. 再做导入脚本
4. 再做一批功能接入
5. 每批都单独验证
